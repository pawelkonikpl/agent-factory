# API campaigns: models, migration, draft CRUD, recipients and stats

> Feature: Add campaigns to the API: the `campaigns` and `campaign_recipients` models and migration, CRUD under `/campaigns/` for drafts, the recipients endpoint and the stats, as specified in `specs/email-sender/backend.md` API-9 (covers B7)

## Context

This is roadmap item API-9 of Phase 4 (Email Sender API). The source of truth is
`specs/email-sender/backend.md`, "API-9: Campaigns" (Requirements, Pitfalls, Acceptance
criteria), plus that file's "Rules for every item". The wire format is in
`specs/email-sender/api-contract.md` §0 (conventions, errors, pagination), §1 (enums), §2
(`CampaignRecipientSchema`, `CampaignStatsSchema`, `CampaignSchema`, `CampaignCreateSchema`,
`CampaignUpdateSchema`, `Page<T>`) and §3.3 (the campaigns endpoints). Background is in
`specs/email-sender/README.md` §5 (layout and layer rules), §6 (soft delete everywhere,
`PrincipalDep` on every endpoint, `selectin` loading, no bare dicts between layers), §10 W-14,
W-16, W-26 and §11 D5 (domain data is global), D6 (`scheduledFor` stored only) and D17 (the
`sending` status exists from the start). This spec restates the backend.md section. Where they
differ, this spec wins.

The `send`/`resend` routes (§3.3, §4) and the "Campaign is being sent" refusals of `PUT` and
`DELETE` for a `sending` campaign belong to API-11 (backend.md API-9 Pitfalls: "Rules for the
`sending` status ... come with API-11"). Nothing in this item sets any status other than `draft`.

What API-2 to API-8 left in `api/` (specs `specs/features/010-` to `017-*.md`):

I ran a trial in a scratch copy of `api/` against a throwaway database (dropped afterwards):

- The models in Requirement 2, autogenerated with `-m "add campaigns"`, give `campaigns`
  (`pk_campaigns`, `ix_campaigns_is_deleted`) and `campaign_recipients` (`pk_campaign_recipients`,
  `ix_campaign_recipients_is_deleted`, the partial unique index, and
  `fk_campaign_recipients_campaign_id_campaigns` and `fk_campaign_recipients_client_id_clients`,
  both `ondelete='CASCADE'`). Each `status` column renders as `sa.Enum('draft', ...,
  name='campaign_status', native_enum=False, create_constraint=True)`.
- **Autogenerate also renders two explicit `sa.CheckConstraint(...)` lines per table** (one named
  `'campaign_status'`, one `op.f('ck_campaigns_campaign_status')`, and the same for

  "ck_campaigns_campaign_status" already exists`, because the `sa.Enum` column already creates it.
  Deleting the four `sa.CheckConstraint` lines fixes it: the database then has exactly
  `ck_campaigns_campaign_status` and `ck_campaign_recipients_recipient_status`, `alembic check`
  prints "No new upgrade operations detected.", and downgrade and upgrade round-trip.
- The ORM stores `'draft'` (the value, not `DRAFT`) with `values_callable`, and mypy strict passes
  on the models. The rendered revision has seven E501 lines to wrap by hand.
- asyncpg stores a naive `datetime` sent to a `timestamptz` column as UTC.

The dev database `emailsender` is shared with the main checkout, whose API migrates it at
startup. Generate the revision and run migration checks against `emailsender_test` only, or the

## Requirements

1. **Models**, in the new module `app/models/campaign.py` (`Mapped[]`/`mapped_column` style):
   - `CampaignStatus(str, enum.Enum)` with `DRAFT = "draft"`, `SENDING = "sending"`,
     `SENT = "sent"`, `FAILED = "failed"`, `SCHEDULED = "scheduled"`, and
     `RecipientStatus(str, enum.Enum)` with `PENDING`, `SENT`, `FAILED`, `BOUNCED` (lowercase
     values).
   - `Campaign(IdMixin, TimestampMixin, SoftDeleteMixin, Base)`, table `campaigns`: `name`
     `String(255)` NOT NULL; `subject` `String(500)` NOT NULL; `content` `Text` NOT NULL; `status`
     NOT NULL with Python-side `default=CampaignStatus.DRAFT`; `sent_at` and `scheduled_for`
     `DateTime(timezone=True)` NULL. `recipients: Mapped[list[CampaignRecipient]] =
     relationship(back_populates="campaign", cascade="all, delete-orphan", lazy="selectin",
     order_by=<CampaignRecipient.id>)`.
   - `CampaignRecipient(IdMixin, TimestampMixin, SoftDeleteMixin, Base)`, table
     `campaign_recipients`: `campaign_id` `ForeignKey("campaigns.id", ondelete="CASCADE")` NOT
     NULL; `client_id` `ForeignKey("clients.id", ondelete="CASCADE")` NOT NULL; `status` NOT NULL
     with Python-side `default=RecipientStatus.PENDING`; `sent_at` `DateTime(timezone=True)` NULL;
     `error` `Text` NULL. Relationships `campaign` (`back_populates="recipients"`) and `client`,
     both `lazy="selectin"`. `__table_args__` holds
     `Index("uq_campaign_recipients_campaign_id_client_id_not_deleted", "campaign_id",
     "client_id", unique=True, postgresql_where=text("is_deleted = false"))`.
   - Both `status` columns use `Enum(<enum>, native_enum=False, values_callable=lambda e:
     [m.value for m in e], create_constraint=True, name="campaign_status")` (and
     `name="recipient_status"`): `VARCHAR` columns with a named CHECK constraint, holding the
     lowercase values.
   - No back-reference on `Client`; `app/models/client.py` does not change. No server defaults.
   - `app/models/__init__.py` also imports `Campaign`, `CampaignRecipient`, `CampaignStatus` and
     `RecipientStatus` and lists them in `__all__`.
2. **Migration.** One new revision, generated in `api/` with
   `uv run alembic revision --autogenerate -m "add campaigns"` against `emailsender_test` at
   `52246cc7e01f`, then corrected by hand:
   - `down_revision` is `'52246cc7e01f'`.
   - `upgrade()` creates both tables, both `is_deleted` indexes and the partial unique index
     (`unique=True`, `postgresql_where=sa.text('is_deleted = false')`). The CHECK constraints come
     only from the `sa.Enum(..., create_constraint=True)` columns: the explicit
     `sa.CheckConstraint` lines autogenerate adds are removed (see the Context).
   - `downgrade()` drops the indexes and both tables, `campaign_recipients` first.
   - Long lines are wrapped so `uv run ruff check .` passes with no `# noqa`. Existing revisions
     and `migrations/script.py.mako` do not change.
3. **Schemas**, in the new module `app/schemas/campaigns.py`, all inheriting `BaseSchema`:
   - Field rules as `Annotated[str, AfterValidator(...)]`, like `CompanyName`:
     - name: trimmed; empty → `ValueError("Campaign name cannot be empty")`; over 255 after
       trimming → `ValueError("Campaign name cannot exceed 255 characters")`; the value is the
       trimmed name.
     - subject: trimmed; empty → "Email subject cannot be empty"; over 500 →
       "Email subject cannot exceed 500 characters"; the value is the trimmed subject.
     - content: empty after trimming → "Email content cannot be empty"; the value is the content
       **as given, not trimmed**. No length limit.
   - `CampaignCreateSchema`: `name`, `subject`, `content` (the rules above),
     `recipient_ids: list[int]` defaulting to `[]`, `scheduled_for: datetime | None = None`.
   - `CampaignUpdateSchema`: `name`, `subject`, `content` as `<rule> | None = None` (the same
     rules when a string is given, the 500 limit on `subject` included), `recipient_ids:
     list[int] | None = None`, `scheduled_for: datetime | None = None`. The service tells an
     explicit `"scheduledFor": null` from an omitted one with `model_fields_set`.
   - `CampaignRecipientSchema`: `id`, `client_id`, `client_name`, `client_email`,
     `status: RecipientStatus`, `sent_at: datetime | None`, `error: str | None`.
   - `CampaignStatsSchema`: `total`, `sent`, `failed`, `pending`, `bounced` (`int`),
     `progress_percentage`, `success_rate` (`float`).
   - `CampaignSchema`: `id`, `name`, `subject`, `content`, `status: CampaignStatus`,
     `sent_at`, `scheduled_for` (`datetime | None`), `created_at`, `updated_at`,
     `recipients: list[CampaignRecipientSchema]`, `stats: CampaignStatsSchema | None`. It dumps
     exactly the contract keys, with `status` as the lowercase value.
4. **Repository**: `CampaignRepository` in `app/repositories/campaign_repository.py`, built with
   an `AsyncSession`, owning every SQLAlchemy query for campaigns:
   - `get_by_id(campaign_id)`: the non-deleted campaign or `None`.
   - `get_all(skip, limit, search)` and `count(search)`: non-deleted campaigns; when `search` is
     neither `None` nor `""`, `name`, `subject` or `content` contains it case-insensitively,
     with `%`, `_` and `\` matched literally (`icontains(term, autoescape=True)`); ordered by
     `created_at desc, id desc`; `count` uses the same filter without `skip`/`limit`.
   - `load_clients(client_ids)`: the non-deleted clients with these IDs (the counterpart of
     `ClientRepository.load_categories`).
   - `create(data, clients)`: a new campaign with `name`, `subject`, `content`, `scheduled_for`
     from `data`, status `draft`, and one `pending` recipient per client.
   - `update(campaign, ...)`: writes the given fields (the service decides which).
   - `set_recipients(campaign, clients)`: soft-deletes the campaign's active recipients, **flushes**,
     then adds one `pending` recipient per client (backend.md Pitfall: otherwise the partial
     unique index can fire on overlapping IDs).
   - `add_recipients(campaign, clients)`: adds a `pending` recipient for each client not already
     an active recipient of the campaign.
   - `soft_delete(campaign)`: sets `is_deleted`/`deleted_at` on the campaign and on each of its
     active recipients.
   - New recipients are appended to `campaign.recipients` with their `client` set to the loaded
     `Client` object, so the returned campaign reflects the committed state without a lazy load.
   - Each write commits and returns the campaign.
5. **Service**: `CampaignService` in `app/services/campaign_service.py`, built with a
   `CampaignRepository`, raising only domain errors and importing nothing from `sqlalchemy`:
   - `get_all(skip, limit, search) -> Page[CampaignSchema]` (items through `to_schema`).
   - `get_by_id(campaign_id)`: `NotFoundError(f"Campaign {campaign_id} not found")` when missing
     or soft-deleted.
   - `create(data)`: resolve the recipients, then create a `draft`. A `scheduledFor` is stored
     and the status stays `draft` (D6).
   - `update(campaign_id, data)`: `get_by_id` (404); if the status is not `draft`,
     `BusinessRuleError("Only draft campaigns can be modified")`; then a partial update: a field
     that is omitted or `null` is not changed, except `scheduled_for`, which is set (to the date
     or to `None`) whenever `scheduled_for` is in `data.model_fields_set`; when `recipient_ids` is
     given (a list, `[]` included), resolve it and `set_recipients` (replacement).
   - `delete(campaign_id)`: `get_by_id` (404), then `soft_delete` (any status in this item).
   - `add_recipients(campaign_id, client_ids)`: `get_by_id` (404); if not `draft`,
     `BusinessRuleError("Only draft campaigns can have recipients added")`; resolve the IDs; then
     `add_recipients`.
   - Resolving recipients [FIX W-26]: drop duplicate IDs, `load_clients`, and if any ID is unknown
     or soft-deleted, `BusinessRuleError("Clients not found: " + ", ".join(...))` with the missing
     IDs ascending ("Clients not found: 3, 7"). Inactive clients are accepted (W-14 is API-11's).
   - `to_schema(campaign) -> CampaignSchema`: only non-deleted recipients, ordered by recipient
     `id`; `clientName` = the client's `company_name`, `clientEmail` = its `primary_email`;
     `stats` = `compute_stats(campaign)`, always present.
   - `compute_stats(campaign) -> CampaignStatsSchema` over the active recipients: `total` and the
     count of each of `sent`, `failed`, `pending`, `bounced`; `progressPercentage =
     round((sent + failed) / total * 100, 2)` and `successRate = round(sent / total * 100, 2)`,
     both `0.0` when `total` is 0.
6. **Wiring** in `app/dependencies.py`: `get_campaign_service(session: SessionDep)` returns
   `CampaignService(CampaignRepository(session))`, and `CampaignServiceDep`. Nothing added to
   `Container`.
7. **Router**: `app/api/campaigns.py`, `APIRouter(prefix="/campaigns", tags=["Campaigns"])`,
   included in `create_app` after the clients router. Every endpoint takes `PrincipalDep` and
   `CampaignServiceDep` and only does HTTP:
   - `GET /campaigns/` with `PageParamsDep` and `search: str | None = None` →
     `200 Page[CampaignSchema]`;
   - `POST /campaigns/`, body `CampaignCreateSchema` → `201 CampaignSchema`;
   - `GET /campaigns/{campaign_id}` → `200 CampaignSchema`;
   - `PUT /campaigns/{campaign_id}`, body `CampaignUpdateSchema` → `200 CampaignSchema`;
   - `DELETE /campaigns/{campaign_id}` → `204`, empty body;
   - `POST /campaigns/{campaign_id}/recipients`, body a **bare JSON array** of client IDs
     (`list[int]`, not wrapped in an object) → `201 CampaignSchema`.
   No `send` or `resend` routes, and no routes without the trailing slash on the collection.

   - `test_campaigns_schemas.py` (no database): the backend.md six for `CampaignCreateSchema`

## Assumptions

- `create`, `set_recipients` and `add_recipients` take the loaded `Client` objects, not
  `client_ids` as backend.md writes. Reason: the service loads them for the W-26 check anyway, and
  a recipient appended without its `client` would need a lazy load (`MissingGreenlet`) when the
  response reads `clientName`; 013 made the same choice for categories.
- `get_recipients_by_ids` is left to API-12. Reason: nothing in this item calls it, and it would
  ship untested.
- `stats` is always filled in, never `null`. Reason: the contract allows `null` but names no case
  for it, and UI-9 reads the stats of every row.
- `bounced` recipients count in `total` but in neither rate's numerator. Reason: that is the
  contract's formula as written.
- A `PUT` or recipients call on a `sending` campaign answers the draft-only message in this item,
  and `DELETE` works for any status. Reason: backend.md moves the `sending` rules to API-11, and
  nothing can set `sending` yet.
- Check order is 404, then the draft rule, then "Clients not found". Reason: a missing campaign
  is reported first, and a non-draft is refused before the body is looked at.
- `"recipientIds": null` on create, and a non-integer item in any recipients array, answer 422;
  on update `null` means "don't change" and `[]` removes every recipient. Reason: the contract's
  create default applies to an omitted field only, and its update rule says `null` means
  unchanged.
- A naive `scheduledFor` is stored as UTC. Reason: that is what asyncpg does (verified), and the
  SPA sends `toISOString()` values with `Z`.
- Recipients of a client that is soft-deleted later stay on the campaign and in its stats.
  Reason: soft-deleting a client does not touch `campaign_recipients`, and API-11 decides what to
  send to them.
- Recipients are listed in recipient `id` order. Reason: a stable order; the contract doesn't say.
- A soft-deleted campaign answers 404 everywhere, so a second `DELETE` is a 404. Reason: same as
  categories and clients.
- Path IDs outside int32 and NUL bytes end in a 500, as in the other areas. Reason: 012's known
  behaviour; fixing it for one area alone would make them differ. A security decision for a
  human.
